# Migration prompt: bring this workspace to Claude Code Genesis Protocol v1.13

**Paste this prompt to the agent that operates an existing workspace on v1.8, v1.9, v1.10, v1.11 or v1.12** (or a local variant of one). Genesis v1.13 is the protocol's version, not a Claude Code release. Every upgraded workspace goes straight to v1.13; no stop at an intermediate version. A workspace on an older version is not upgraded by this prompt: a workspace with no v1.8 marker is best re-bootstrapped from the current protocol ([claude-code.md](claude-code.md)), carrying its decisions and PLAN forward (Entry paths below). The prompt upgrades the workspace's governance in place. It is not a fresh bootstrap: the code, decisions, PLAN, operator ledger and local rules already exist and must survive. In this prompt AGENT is the agent running it and HUMAN is the operator.

**Input:** alongside this prompt, HUMAN provides the full v1.13 protocol text (or a local path to it), and may add a handout: a short note naming rulings that already hold for every project, each with its qualified id (B2 item 1), and any identity answers HUMAN already knows for this project (B3 item 2). The guide is run only from a commit on the main line of the repository it comes from, so the shared install's block, its tools and the rulings the handout names resolve there (never from an unmerged release branch); the handout cites that commit. AGENT reads both before planning. The workspace's working language governs generated content; structures and filenames stay as written.

**The point of v1.13, and the expected shape of the work:** v1.13 is v1.12 plus machines and identity: one home machine per project (a workstation or an always-on hub), collaborators on any other clone, and identities settled by an interview and pinned per project (v1.13 Phase 0 §7 and Phase 1). Most entrants take three layers here: Phase B1 is v1.11's working practice (handover, the lead and its helpers, model tiers, the stage), Phase B2 is v1.12's corrections and the CLAUDE.md cut, Phase B3 is v1.13's machines and identity. On a rig that ran the shared install's adoption prompt, the posture items are expected ALREADY-LOCAL. The main work is carrying the CLAUDE.md cut (B2 item 10) without trimming any local rule, and filling the identity interview from evidence so that only the gaps are asked (B3 item 2).

## Entry paths

Decided from evidence, not from the version label. AGENT names the surface that would show each marker and checks that surface (settings files at every scope, CLAUDE.md, the README, the verify suite, the operator ledger, the decision log, PLAN.md, the agent files, the clone's git config). **Markers count only on the main line:** a marker present only on a branch or only in uncommitted files is listed separately and does not count. **A marker counts only with its practice:** each marker is checked against the item it marks, not by its file alone; a Handoff block whose triggers are written nowhere is present for B1 item 5 and missing for B1 item 6.

- **v1.7 markers:** a CLAUDE.md size check in the verify suite; an operator ledger (open items and rulings); capabilities named conditionally ("if the current build offers one").
- **v1.8 markers:** a recorded permission posture and a deny floor (v1.8's rules). A second settings file loaded with `--settings`, or a recorded removal of one, is further v1.8-or-later evidence; its absence is not a missing marker.
- **v1.9 markers:** the posture is one setting (the mode), not a second settings file; the deny floor is derived from what the machine can reach, not from the ask list; bus mode, where present, is one shared install rather than a per-repo copy.
- **v1.10 markers:** zero `ask` rules in the merged settings of a rig that runs unattended; `AskUserQuestion` barred unattended; the postures recorded as rulings.
- **v1.11 markers:** a dated Handoff block heading PLAN.md's Current state, with its triggers written in CLAUDE.md; §11's five-part brief for helpers; `model` frontmatter on the agents; a ruled stage (shaping, building or commercial); the short decision-task format.
- **v1.12 markers** (each that applies; a solo rig carries no §13 and no bus-mode block): §13 is the project's contract plus a pointer to the bus's `guide()`, with the mechanics `guide()` covers removed (a pointer added above the old mechanics is the marker without its practice); a commands slot in §05; the hard line's exception records HUMAN's quoted answer on the bus (the recorded answer); the bus-mode block of the revision that names three wake triggers (a startable task, an unread post addressed to the session, unassigned work that has appeared since the last reading); a repo that carries a pointer to the block, or is the block's source, marks it by text that agrees with the block (B2 item 9).
- **v1.13 markers** (each that applies): the README records the home machine and carries `## Identity` and `## Identity pins` (names only) with the sentence on where values live; the verify suite carries the identity check (v1.13 Phase 3 item 8); §05's commands slot names `verify`; §10 names the home; the clone has its own git author; where the project carries the bus-mode block, the revision that names the shared install home-relatively; where the rig runs unattended, template §15's unattended-chain paragraph.

**The label** is the version named in the most recent dated migration decision (the project's decision recording its last Genesis move, found by its title or the version it names) or PLAN entry; none if absent. A decision that cuts a protocol version and also repairs the repo is a migration of the repo only where it says the repo now runs that version. A PLAN entry sets the label only where it says the repo now runs that version; one that cites a cut decision follows that decision's rule. Conflicting entries are reported, and the most recent dated one is the label; where two labels stay defensible, both are reported (the route comes from the evidence either way). Commit messages never set the label; an undated PLAN entry counts only with a dated decision. **Mixed evidence:** with the v1.7 layer complete, the path starts at the phase of the oldest layer with a missing marker and runs through B3; a phase entered for a missing marker runs only its missing items, each present one cited as ALREADY-LOCAL. Layers map to phases: v1.8, v1.9 and v1.10 markers to B0 (a v1.8 layer missing entirely means a fresh start, below), v1.11 markers to B1, v1.12 markers to B2, v1.13 markers to B3. A marker HUMAN has declined by ruling counts as present for routing, cited as that ruling, and a ruling that the rig never runs unattended or on the bus counts as its v1.8 layer; the budget rule then counts by hand.

When the label and the evidence disagree, the evidence decides the route and the label is reported as stale (Phase D item 2's version line then corrects it).

Routes, checked in this order:

- **An earlier migration branch is checked out, or waiting unmerged:** checked first; it pre-empts every other path. A migration branch is one named for a Genesis migration (such as `feature/genesis-v1.12-migration`) or whose unmerged diff carries a migration's governance edits (CLAUDE.md, `.claude/`, the operator ledger, or a migration decision). Stop and resolve it: review the branch's net diff (`git diff main...<branch>`) against the current text of what it carries, then land or reject it; content that would contradict a main-line record (Phase A item 8) lands only on HUMAN's ruling. This run then starts again from the main line. In the repository that publishes this protocol, the protocol's own unmerged release branch is not a migration branch: it merges first, through that repository's gates; a rehearsal run on it lists its markers as not on the main line, and the report names the merge as a precondition.
- **No CLAUDE.md, and a shaping skeleton** (a README with `## Identity`, PLAN.md, a brief): not an upgrade. The project is bootstrapped with v1.13 at "build it" (v1.13 Phase 1, "From a shaping skeleton"); stop and report that.
- **Every marker from v1.7 through v1.13 that applies is present and the label is v1.13:** Phase A only, then the report. Otherwise mixed evidence decides.
- **From v1.12:** Phase A; Phases B1 and B2 as verification only, each item cited ALREADY-LOCAL or reported missing; then Phase B3.
- **From v1.11** (if one adopted it): Phase A; Phase B1 as verification only, each item cited ALREADY-LOCAL or reported missing (lanes removed under v1.11's stale reason are reported, and working lanes return only on HUMAN's answer); then Phases B2 and B3.
- **From v1.10:** Phase A, then Phases B1, B2 and B3.
- **From v1.8 or v1.9:** Phase A, then Phases B0, B1, B2 and B3.
- **From v1.2 or earlier:** re-bootstrap from the current protocol ([claude-code.md](claude-code.md)) instead.
- **Any v1.7 marker missing, no v1.8 marker at all, or a label below v1.7 (v1.3 and later), whatever later markers exist:** not an upgrade from here. Re-bootstrap from the current protocol ([claude-code.md](claude-code.md)), carrying the decisions, PLAN and operator ledger forward; stop and report that.

## Prime directives (read before touching anything)

1. **Branch first.** All work on `feature/genesis-v1.13-migration`, cut from the main line after any earlier migration branch is resolved (Entry paths); nothing lands on the main line until verification passes and HUMAN approves.
2. **Local inventions are protected.** On conflict between v1.13 and a local rule, the local rule wins and AGENT flags it to HUMAN. A stricter local rule is not a conflict: a rule that leaves a HUMAN-answered task for HUMAN to close is stricter than v1.13's hard-line exception, and it stays as written. A local ruling that loosens live rule text is a document-loop flag for HUMAN; the migration never resolves it, with one exception: where the ruling is the project's own and v1.13 carries the same rule (the posture, B2 item 1), the live text is restated to the ruling, cited by its id, and the report says so on its `posture:` line.
3. **Governance only.** CLAUDE.md, `.claude/`, root docs and document scaffolding; never code, never the meaning of a decision file. Six named exceptions: re-syncing a tool copy that a ruling keeps synced from a shared install; a hook script's `ask` answer changed as B2 item 2 says, with its tests; a false claim corrected in a comment or printed message of the repo's own scripts or tools (B0 item 7), with no change to logic; a literal user path corrected in a comment (B3 item 7), with no change to logic; on HUMAN's go, the identity check added to the verify suite (B3 item 4); and, on HUMAN's go, an existing size or link check extended to the move list's pointers and rules files (B3 item 11).
4. **Plan, then gate.** HUMAN's go before any file modification.
5. **Adopt, never build a second one.** Where an equivalent structure exists (a handover section, a sequence, a ledger, a reviewer, an identity section in the README), v1.13's item maps onto it; a parallel copy is drift.
6. **The hard line holds during the migration.** AGENT never answers a decision task assigned to any human. One exception, for HUMAN only: when HUMAN states the answer in this session, AGENT records the stated option as HUMAN's answer with HUMAN's words quoted (the bus's recorded answer). If the bus refuses it, the task stays open with the ruling recorded, never cancelled. Anything less explicit, a relayed answer included, stays open.
7. **Never stage, stash or revert uncommitted work** in the tree; it belongs to whoever left it.
8. **Never edit user-level or managed files** (user settings, user CLAUDE.md, auto memory, the machine's global git config, anything outside this repo): report what is found there and leave it.
9. **Never edit a verbatim-pasted block in place** (a block another source owns and this repo carries word for word); re-copy it from its source or leave it.
10. **Name the actor.** In anything another party reads and acts on (decision-task options, open items, handover text, pull-request bodies), write AGENT and HUMAN or the real handles, never "you" or "I".
11. **The workspace's own rules still apply:** verification after changes, atomic commits, explicit pathspecs, a staged-scope check before every commit.
12. **Never add or change `defaultMode` at any scope.** The mode is chosen at launch; a project-level one is reported (B2 item 1), never edited.
13. **Never edit the project's shipped artifacts in place:** frozen baselines, the meaning of a decision, dated records, released versions. A correction is a new record that cites the old one.
14. **Merge and push only through the project's own gates:** its suite, its reviewer, HUMAN's go, and its merge rule. A public remote only on HUMAN's go.
15. **Never print a pin's value or a credential.** `.claude/settings.local.json` is read key-only; a check on a pin's value prints only the pin's name and pass or fail. Pin values are written by HUMAN or whoever runs the machine, or by AGENT on HUMAN's go with an edit that adds only those keys and prints nothing else from the file.

## Rehearsal (read-only, on HUMAN's request)

Where HUMAN asks for a rehearsal first, AGENT runs Phase A, classifies Phases B0, B1, B2 and B3, and writes the Phase C report with `rehearsal` in its header. It changes nothing: no file writes, no commits, no branches, no bus calls, and no reads of credential contents (whether a credential file exists is enough; a project-local settings file is read key-only, as in Phase A item 4, or not at all). Read-only commands are allowed: version flags; read-only git (`status`, `log`, `diff`, `show`, `ls-remote`, `ls-files`, `ls-tree`, `rev-parse`, `branch --list -a`, `for-each-ref`, `worktree list`, `stash list`, `remote get-url`, `config --get` and `config --show-origin --get-all`); a cloud CLI's configuration listing where it prints account and project names only; a code-host CLI's status where token lines are dropped, and its read-only lookup of the remote owner's type (for example `gh api users/<owner> --jq .type`); the repo's own verify suite where it writes nothing; a key-only settings parse with optional locks off (`GIT_OPTIONAL_LOCKS=0`), or the shared install's read-only preflight, which reads only the repo it is launched from, so for any other repo the key-only parse is used; and a pin check that prints only names and pass or fail and runs offline, never one that fetches or writes (directive 15). A read-only check that a deny refuses is reported "unknown (denied)" and the run moves on. A helper without a shell takes shell-only facts from the lead, each labelled as the lead's. Where the rehearsal runs on a machine other than the one the upgrade will run on, each machine fact is labelled "this machine (<name>), not the upgrade's". The report lists under "not checked in a rehearsal": `claude doctor` and `/status` (the load proof); the installed mods; the live `guide()` and `list_sequences`, so each §13 removal is listed as "would remove if the live guide() covers it"; the board audit (human tasks on agent handles, lane addressing); the B2 item 9 source comparison unless the source's main was fetched; the other machines named in the move-home checklist (B3 item 10); and, wherever the command or file that shows them could not be run or read, binary versions, the release channel, hook-type and model-alias acceptance, the managed-settings file, whether a load gate runs, pin values on this machine, which logins use the keychain, and commit identities where `git log` could not run.

## Phase B2: The v1.12 layer (v1.8-v1.11 entrants; verification only from v1.12)

Classify each APPLY (file: change) / ALREADY-LOCAL (where) / N/A / HELD (why):

1. **Posture (Phase 0 §6).** If HUMAN's handout states that the posture is ruled for every project, record it in the project's rulings ledger under the project's own next ruling id, citing the source as the handout gives it (owner and project, ruling id) plus a commit ref (B1 item 8), and do not ask; if the project's own ledger already holds the ruling, cite it; otherwise ask (Bypass plus the deny floor, with its trade in plain words), and never choose. Live text that names two postures, calls `auto` an unattended posture, or claims a project file sets the mode is restated as v1.13's single posture, citing the ruling (directive 2's exception); dated records stay. A project-level `defaultMode` of `bypassPermissions` or `auto` is reported as not taking effect (directive 12). If HUMAN declines Bypass, the project runs attended only and carries no unattended posture.
2. **Hooks answering `ask`** (a rig that runs unattended or in bus mode). For each path from Phase A item 4: where AGENT starts the action, the script is changed as the shared install's adoption prompt says under "Hooks that answer `ask`" (in its section "Make this repo freeze-free"), with that part's proof; the toggle HUMAN speaks stays `ask`. A path that answers `ask` only when the harness's input does not parse is reported, not changed. A local claim that a hook `ask` does not prompt under Bypass contradicts v1.13 §6: report it with the builds, where recorded (an unrecorded build is reported as unknown), as a question.
3. **Per-project cloud-CLI denies.** For each authenticated cloud CLI, the project's settings deny its secret-reading and remote-shell commands, where the CLI has them (for example `Bash(gcloud secrets:*)` and `Bash(gcloud compute ssh:*)`), unless the project records a need. If the project's own ledger already holds the ruling, AGENT cites it, as item 1 does; if HUMAN's handout states this is ruled for every project, AGENT records the ruling as item 1 does. Either way AGENT applies the denies and asks only whether the project records a need for either, and about any authenticated cloud CLI the ruling does not name. With no ruling, the denies are asked, never assumed.
